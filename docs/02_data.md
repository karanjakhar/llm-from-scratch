# Stage 02 — The Data Pipeline

At 125M parameters, **the data is most of the model.** Architecture tweaks
move loss by a few percent. Data choices move it by a lot more. This stage
turns ~3 GB of compressed GitHub JSON and one fineweb-edu parquet file into
flat binary token arrays that the training loop can sample from without ever
starving the GPU.

What this stage builds, in order:

```
download (pinned revisions)
   → stream documents
   → filter (license)
   → split train/val by REPOSITORY hash
   → tokenize in parallel, append <|endoftext|> after each document
   → write uint16 memmaps:  train_code.bin  train_en.bin  val_code.bin  val_en.bin
   → manifest.json   (everything needed to reproduce the bins exactly)
then
   → a batch sampler that mixes code/English at a runtime ratio
```

---

## 1. Why data quality dominates

The canonical evidence is about code specifically:

| Model | Params | Training data | HumanEval pass@1 |
|---|---|---|---|
| CodeParrot | 1.5B | ~raw GitHub Python | ~4% |
| phi-1 | 1.3B | ~7B tokens, heavily filtered "textbook-quality" code + synthetic exercises | ~50% |

Same parameter count, more than a 10x gap, and the difference is almost entirely
data selection. A small model has no spare capacity to spend memorizing
boilerplate, license headers, and auto-generated tables. Every token of junk is
a token of capacity not spent on code structure.

**We are closer to the CodeParrot end of that table, on purpose, and that
should be said plainly.** `codeparrot-clean` has light heuristic filtering. The
quality-scored alternative (`python-edu`) ships metadata only and needs ~500k
S3 fetches (see `docs/datasets.md`). Getting the pipeline right on accessible
data first, and treating better-filtered data as a later, measurable upgrade,
is the deliberate tradeoff.

## 2. What is actually in the corpus — measured, not assumed

Profile of shard 1 of `codeparrot/codeparrot-clean` (revision `35a59fb`):

```
alpha_frac      ≥ 0.25 for all      (p1 0.43, p50 0.61)
```

Extrapolated: 54 shards ≈ **5.4M files, ~53 GB of Python**.

Three of those numbers changed the plan.

**Upstream filtering already happened.** CodeParrot's cleaning removed
auto-generated files, files with very long lines (`line_max ≥ 1000`, usually
minified or data blobs), and files with low alphabetic fraction (`alpha_frac ≤
0.25`, usually embedded data or base64). Re-applying those filters would be a
no-op, so we do not. The lesson generalizes: **profile before filtering.**
Filters copied from a blog post onto data that was already cleaned do nothing,
and filters copied onto data with a different distribution do damage.

**Repos are scattered across shards.** 47k repos in 100k files means files
from one repository land in many shards. A train/val split by shard would
therefore leak whole repositories into both sides. §5 deals with this.

**Licenses split ~58/42.** By bytes:

## 3. Filtering: license

We keep **permissive licenses only** — apache-2.0, mit, bsd-2/3-clause,
unlicense, isc, cc0-1.0. That is 57.7% of bytes.

Whether training on copyleft code creates obligations for the model is a
genuinely unsettled legal question. Permissive-only is the conservative choice,
it is what makes the trained weights publishable without an asterisk, and at
~53 GB available against ~6 GB needed, it costs us nothing we would have used.

What breaks without it: nothing technical. The model is not worse. This is a
filter for the project's integrity, not its loss curve, and it is worth knowing
which kind of filter you are writing.

## 4. Deduplication

### Why duplicates hurt more than they seem to

GitHub is full of copies: forks, vendored libraries, copy-pasted utilities,
`setup.py` templates, Django migrations. A file that appears 50 times gets 50x
the gradient weight of a file that appears once, and the model memorizes it.
At small scale that is capacity wasted on recall. Worse, duplicates that
straddle the train/val split make validation loss **measure memorization
instead of generalization**.

### Exact dedup — upstream did it, we verify it

Exact duplicates are cheap to find: hash the content, keep the first copy.
CodeParrot did this across the full dataset (the `hash` column; `copies` says
how many copies existed before). We re-hash with our own function across every
shard we use and report the duplicate rate, because "the dataset card says it
is deduplicated" is a claim, and claims get checked.

### Near-duplicate dedup — built, because the leakage number said so

A fork that renamed one variable has a different hash. Exact dedup misses it.
The standard tool is **MinHash + LSH** (`llmfs/data/dedup.py`):

1. **Shingles.** Represent each file as the *set* of its word 5-grams, where a
   "word" is a `\w+` run. Ignoring whitespace and punctuation means a fork run
   through a formatter still matches its original.
2. **Jaccard similarity** `|A ∩ B| / |A ∪ B|` between two shingle sets measures
   overlap, from 0 to 1.
3. **MinHash.** Apply P = 120 independent hash functions to every shingle and
   keep the minimum for each. For any single function,
   `P(min_A == min_B) = Jaccard(A, B)` exactly, so the fraction of the 120
   positions that agree is an unbiased estimate of Jaccard, with standard
   deviation at most `sqrt(0.25/120) ≈ 0.046`.
4. **LSH banding.** Cut the 120 values into 20 bands of 6. Two files become
   *candidates* if any band matches exactly. The probability of that is
   `1 - (1 - J^6)^20`, an S-curve: ~27% at J = 0.5, ~92% at J = 0.7, ~100% at
   J = 0.9. Each file is compared with a handful of candidates instead of all
   700k others, which avoids the O(n²) blowup.
5. **Verify** each candidate pair by its estimated Jaccard ≥ 0.7, **union-find**
   the matches into clusters, and keep one file per cluster.

Which copy survives matters. **When a cluster spans train and val, the train
copy is kept and every val copy is dropped.** Dropping the train copy instead
would leave the val file in place with its near-twin gone from train. That
looks equivalent, but it keeps a val set chosen by "which repos happened to be
forked", so the train copy wins.

Two implementation details that silently break this if missed:

- **No `hash()`.** Python's built-in `hash` is salted per process. Signatures
  are computed in 18 worker processes, so with `hash` every worker's
  signatures would be incomparable with every other's and nothing would ever
  match. The module uses `zlib.crc32` and a multiply-add-shift hash family; a
  test computes signatures in spawned processes and asserts they are identical.
- **Jaccard is over sets.** A shingle repeated 40 times counts once; the
  `np.unique` is part of the definition, not an optimization.

### What it found (12 shards, 729,865 permissive files, 149 s)

| | |
|---|---|
| near-duplicate train files dropped | 205,241 / 726,664 (**28.2%**) |
| val files dropped | 1,264 / 3,201 (**39.5%**) |
| …of which had a near-copy **in train** | **1,258** |
| clusters containing duplicates | 87,331 |

More than a quarter of "deduplicated" GitHub Python is near-duplicate, and
almost every dropped val file was a near-copy of something in train. **Without
this step, ~40% of the code validation set would have been memorization tests.**

## 5. The train/val split — by repository, by hash

### Why "by file" is wrong for code

Files in the same repository share imports, helper functions, naming
conventions, license headers, and sometimes whole copied blocks. If
`utils.py` from repo X is in train and `helpers.py` from repo X is in val, the
model is graded on text it has effectively seen. Validation loss comes out
optimistic, and the gap between validation loss and real-world quality is
exactly what validation exists to measure.

The fix: assign whole repositories to one side.

### Why by hash, not by random draw

```python
def split_of(repo_name: str) -> str:
    h = int.from_bytes(hashlib.blake2b(repo_name.encode(), digest_size=8).digest())
    return "val" if (h % 10_000) < VAL_PER_10K else "train"
```

- **Deterministic.** Same repo, same side, every run, on every machine. No
  random state to save or forget.
- **Streamable.** The decision needs one record, not a global shuffle of 5M
  files. Shard order does not matter, which is required because repos are
  scattered across shards (§2).
- **Stable under growth.** Add 10 more shards later and every existing repo
  stays on the side it was already on. A random split would reshuffle and
  silently put old val repos into train.

For English documents (no repo), the same function hashes the document id.

### Val sizing

0.5% of repositories go to val. Validation loss needs only ~10M tokens to be
stable to two decimal places, and every val token is a token not trained on.

### The ablation for this stage: what do the split and the dedup each buy?

Measured in `run.py leakage`, without training anything. For every val file,
take each non-trivial line (stripped, ≥ 20 chars) and check whether it appears
verbatim anywhere in train. Two views of that number:

- **All lines.** Inflated by boilerplate (license headers, common imports) that
  is in train under any split. That makes it a ceiling, not a clean signal.
- **Rare lines**: lines found in ≤ 5 files across the whole corpus. Those are not
  boilerplate. A rare line on both sides of the split is a copy.

Results on shards 1-2 (~119k permissive files):

| split | near-dedup | val lines in train | **rare** lines in train | val files >50% leaked |
|---|---|---|---|---|
| file-level | no | 56.3% | 43.9% | 48.6% |
| repo-level | no | 47.6% | 34.4% | 43.3% |
| file-level | yes | 29.6% | 21.7% | 27.4% |
| **repo-level** | **yes** | **15.1%** | **8.1%** | **13.8%** |

What the table shows:

1. **The repo split alone was not enough.** Before near-dedup, 43% of val files
   had most of their lines in train, mostly through forks under other repo
   names, which a repo split cannot see.
2. **Near-dedup alone is not enough either.** With dedup but a file-level
   split, rare-line leakage is still 21.7%. Same-repo files share helpers and
   copied blocks that are not near-duplicates *as whole files*.
3. **They are complementary.** The file-vs-repo gap *grows* after dedup
   (+9.5 → +13.6 rare-line points). Once cross-repo copies are gone,
   within-repo sharing is the main leak, and only the repo split catches it.
4. **The residual 8.1% is real and known.** These are probably partial copies,
   e.g. one vendored function inside an otherwise original file, which
   whole-file Jaccard cannot detect. Closing it would need line- or
   function-level dedup. We note it rather than chase it: val loss will be
   slightly optimistic, and Stage 22's HumanEval/MBPP numbers do not depend on
   this split at all.

The curriculum originally listed "document-level vs token-level shuffling" as
this stage's ablation. That needs a training loop to observe, so it moves to
Stage 08. The leakage ablation measures something real now.

## 6. Tokenize once, store as `uint16`

Tokenizing on the fly during training wastes CPU every epoch and, with a
pure-Python tokenizer, would starve the GPU outright. So tokenize everything
once and store the ids on disk.

**Why `uint16`:** our vocab is 8192 + 4 specials, well under the 65,535 a
`uint16` can hold. That is 2 bytes per token instead of 8 for `int64`:

```
2.5B tokens × 2 bytes = 5 GB      (uint16)
2.5B tokens × 8 bytes = 20 GB     (int64 — PyTorch's default index dtype)
```

The cast to `int64` happens per batch on the fly, a few KB at a time.

**Why `np.memmap`:** the file is mapped into the address space and the OS pages
it in on demand. A 5 GB array costs essentially no RAM until touched, and
repeated reads hit the OS page cache. No custom loader, no sharding logic.

**Parallelism:** documents are tokenized in a `multiprocessing.Pool` with
`imap` (ordered), so the output is byte-identical regardless of worker count.
Each worker loads the tokenizer once and keeps its own chunk-encoding cache
(§8).

## 7. Packing: concatenate, separate with `<|endoftext|>`

Documents vary from 100 bytes to 900 KB. The model sees fixed windows of
`T` tokens. Two ways to bridge that:

**Padding:** one document per row, pad to `T`. With median file ~1.5k tokens
and `T = 1024`, short files waste most of the row and long files get truncated.
Measured waste on real corpora is commonly 30-60% of compute.

**Packing:** concatenate every document into one flat stream with an
`<|endoftext|>` token after each, and cut windows from the stream anywhere.
Zero padding, zero waste.

```
... def foo():\n    return 1\n<|endoftext|>import os\nfrom pathlib ...
                              ^ document boundary
```

**The cost of packing:** a window can straddle a boundary, so the model attends
from tokens of document B back into the end of document A. It learns that
`<|endoftext|>` means "what came before is irrelevant", and at pretraining
scale the measured harm is small, which is why GPT-2 and GPT-3 did exactly
this. The fix when it matters is **document masking**: a block-diagonal
attention mask so attention cannot cross a boundary. Long-context training and
SFT packing (Stage 16) use it. Here it is not worth the complexity.

## 8. Making our tokenizer fast enough

Stage 01's encoder runs at 0.53 MB/s. The corpus is ~7.5 GB:

```
7.5 GB / 0.53 MB/s ≈ 4 hours, on one core
```

Two changes, both in `llmfs/tokenizer/`:

1. **Chunk cache.** Pre-tokenized chunks follow a Zipf distribution. In 20 MB of
   real Python there are 4.9M chunks but only 110k unique ones: `"    "`,
   `" self"`, `" ="`, `" return"` repeat endlessly. Cache `chunk → ids` and the
   expensive merge loop runs only on chunks never seen before.
2. **Processes.** 20 CPU threads available, tokenization is embarrassingly
   parallel across documents.

The output must be **identical** to Stage 01's encoder. A test asserts it, on
real files. A faster tokenizer that produces different ids is a different
tokenizer.

## 9. Mixing code and English at runtime, not at write time

We write code and English into **separate** binaries and mix them in the
sampler:

```python
source = "code" if rng.random() < 0.85 else "en"
```

Baking the 85/15 mix into one file would mean re-tokenizing the corpus to try
100/0 or 70/30. Stage 10 runs exactly that ablation. With separate files it is
a command-line flag.

Mixing is **per sequence, by token count**: each training window is 100% one
source. 85% of windows are code, so 85% of training tokens are code.

Separate **val** files too — `val_code.bin` and `val_en.bin` — because a single
mixed val loss hides the tradeoff Stage 10 is trying to see: more English may
cost code loss while buying instruction-following.

## 10. Sampling windows from the stream

### The simple sampler: random offsets

```python
ix = torch.randint(len(data) - T - 1, (B,))
x  = stack([data[i   : i+T  ] for i in ix])     # (B, T)  inputs
y  = stack([data[i+1 : i+T+1] for i in ix])     # (B, T)  targets, shifted by one
```

Valid because every offset is an equally good place to start predicting. No
epoch bookkeeping, trivially resumable. nanoGPT does exactly this.

### Why it is wrong for us specifically: coverage

With replacement, a given token is missed by every one of `S` windows with
probability `(1 - T/N)^S ≈ e^(-S·T/N) = e^(-epochs)`. After one epoch's worth
of samples:

```
never seen:   e^-1           ≈ 37%
seen once:    e^-1           ≈ 37%
seen twice+:  1 - 2e^-1      ≈ 26%
```

**37% of the data is never trained on in the first epoch.** When data is
plentiful that is irrelevant. We have ~2.1B tokens for a model that wants
~2.5B, so ~1.2 epochs (see `docs/datasets.md`), and wasting a third of the data
while double-counting a quarter is a real cost.

### The sampler we use: shuffled non-overlapping windows

Cut the stream into `⌊(N-1)/T⌋` non-overlapping windows, shuffle their order
once per epoch with a seeded permutation, and walk it. Every token is seen
exactly once per epoch. Resuming needs `(epoch, position)`, two integers.

Both samplers are implemented. A test checks the coverage property: one epoch
of the shuffled sampler covers 100% of windows exactly once, and one epoch's
worth of random sampling covers ~63%.

## 11. Not starving the GPU

The workhorse model needs ~30-80k tokens/s (Stage 00 compute table). The
loader has to beat that comfortably, or every optimization in Stage 09 is
wasted waiting on data.

A batch from a memmap is a few hundred KB of contiguous reads, an `int64` cast,
then a host-to-device copy. Two details matter:

- **Pinned memory** (`.pin_memory()`) lets the copy use DMA, and
- **`non_blocking=True`** lets that copy overlap with GPU compute instead of
  stalling the Python thread.

`run.py` measures loader throughput in tokens/s with and without these, against
the model's requirement. If the loader is 100x faster than needed, a
multi-worker `DataLoader` is unnecessary complexity, and we will not add one.

## 12. Reproducibility: the manifest

"Trained on codeparrot-clean" does not reproduce anything. `manifest.json`
records:

- dataset ids **and revision hashes**, and exactly which shard files
- filter predicates (license allowlist) and the val fraction
- the tokenizer file and its SHA-256
- per-binary token counts and document counts
- the exact-duplicate rate found

With the manifest and the same code, the binaries reproduce byte for byte.

## 13. Build order

1. `download.py` — fetch pinned shards + one fineweb-edu parquet.
2. `llmfs/data/corpus.py` — stream documents, license filter, repo-hash split.
3. Production tokenizer (Stage 01 domain work, `stages/01_tokenizer/train_production.py`)
   — train on a train-split-only sample; compare vocab 8192 vs 16384, digits
   grouped vs split; pick one.
4. `llmfs/tokenizer/` — fast cached encoder, proven identical to Stage 01.
5. `prepare.py` — parallel tokenize → four `.bin` files + `manifest.json`.
6. `llmfs/data/loader.py` — random and shuffled samplers, code/English mixing.
7. `run.py` — leakage ablation, dedup rate, loader throughput.

### Acceptance criteria — results on the real corpus (2026-10-25)

- [x] No repository appears in both train and val: guaranteed by construction
      (`split_of` hashes `repo_name`) and asserted in `test_data.py`.
- [x] Every document ends with exactly one `<|endoftext|>`: EOT count equals
      document count in all four bins (521,423 / 720,855 / 1,937 / 3,656), and
      every bin ends in EOT.
- [x] `decode(bin)` reproduces source exactly: first 200 documents of
      `train_code`, `val_code` and `val_en` byte-identical. The first `val_en`
      attempt "failed" at document 174, which turned out to be a verbatim copy of
      a `train_en` article that the shared deduper had correctly removed. The
      check was wrong, not the bin.
- [x] Fast tokenizer identical to Stage 01 on real files (test, now unskipped).
- [~] Reproducible bins: worker-count invariance is tested at small scale and
      the document stream is deterministic by construction. A full second
      `prepare.py` run comparing SHA-256s has **not** been done.
- [x] Shuffled sampler covers every window exactly once per epoch (test).
- [x] Loader throughput ≥ 10× the requirement: 56-140M tokens/s, i.e.
      **700-1,750×** the workhorse's ~80k tok/s. The CPU-only row ran first
      against a colder page cache, so the rows are not cleanly comparable with
      each other, but all clear the bar by two orders of magnitude. No
      multi-worker `DataLoader` needed.
- [x] Leakage measured and logged (§5).

### What came out

| bin | documents | tokens | bytes/token | near-dups dropped | exact dups dropped |
|---|---|---|---|---|---|
| `train_code` | 521,423 | 1,330.1M | 3.267 | 205,241 | 0 |
| `train_en` | 720,855 | 1,016.9M | 3.390 | — | 1,476 |
| `val_code` | 1,937 | 4.9M | 3.214 | 1,264 | 0 |
| `val_en` | 3,656 | 5.2M | 3.379 | — | 13 |
| **total** | | **2,357M** | | | **4.4 GB on disk** |

Tokenization took ~4.5 minutes at ~36 MB/s across 18 workers, about 4× below
the workers' combined capacity. The suspected bottleneck is the single main
process reading and JSON-parsing the gzipped shards; it has not been profiled.

### Token budget

- **Workhorse (~50M params, ~1B tokens at 85/15):** needs ~0.85B code tokens.
  We have 1.33B. Covered with room to spare.
- **Capstone (~125M params, ~2.5B tokens at 85/15):** needs ~2.1B code tokens.
  We have 1.33B, which would mean ~1.6 epochs. Before Stage 11, download ~8 more
  shards (~110M code tokens each after dedup; the dedup rate will rise as the
  corpus grows), re-run `dedup.py` over all of them, and re-run `prepare.py`.
  Not needed until then.

care about (here, leakage) directly. Every major decision in this stage came
from a measurement, and two of them reversed the plan.
